# Pilot acceptance — 3.3.0

Release status: **READY_FOR_PILOT**, not production validated. The offline suite
checks orchestration and real local encoding, not provider availability or creative quality.
Stop adding speculative features. Change this release only for a reproducible failure
or a requirement demonstrated by the pilot.

## Small first production

Use a new project and supplied source material, independent of previous generated
assets. Target four short shots, about 20–30 seconds after editing, subject to actual
provider duration support. Build the graph using `PRODUCTION_GRAPH.md`.

1. A source-backed establishing frame with an exact historical text/geometry layer.
2. A reachable, restrained camera move based on the approved visual reference.
3. A continuation testing identity and a planned join; if unsupported, use the
   declared hard-cut alternative and record that the original route was not tested.
4. A deterministic detail/end card testing exact Chinese typography and local finishing.

The agent reads evidence, prepares contracts, calls available image tools and Flow,
downloads results, records receipts, reviews candidates, builds the preview, assembles,
mixes and verifies. Do not turn routine tool operations into manual user tasks.
Human decisions remain G1 story, G2 visual/animatic and G4 picture lock; G3 is used
only for an actual motion escalation. Reuse existing explicit authorization.

## Before the first live request

- Observe current tool/account capabilities. Record the actual image model name,
  whether it is selectable, Flow mode/model, durations, reference limits and evidence
  time. A desired name such as GPT Image 2.5 is not proof of an exposed model.
- Use one candidate per initial attempt. Set explicit authorized provider output
  caps for the pilot; obtain missing spending authorization as one bundled decision.
  Do not buy credits or expand limits automatically.
- Compile, synchronize and inspect the runboard. Every required unit must be
  dispatchable or have an understood dependency; no silent omissions.

## Acceptance evidence

| Area | Pass evidence |
|---|---|
| Actual tools | Real provider handle/receipt, observed model/mode and downloaded media; no fixture receipts |
| Historical fidelity | Source-linked review and exact protected overlay verification; uncertain facts stay unresolved |
| Image workflow | Reference-based generation/edit demonstrated; selected files match reviewed hashes |
| Flow motion | Full clip review for identity, geometry, camera path and endpoints, plus intended join review |
| Recovery | Interrupt agent orchestration after a real receipt, resume by observing that existing attempt; no duplicate submission or reservation |
| Local finishing | All units present in order, timing within one frame, subtitles/audio inspected, full final-file decode passes |
| Human gates | Decisions refer to the actual reviewed files; later edits invalidate affected approvals |
| Delivery | Playable final file, receipts, review record, source lineage, gate history and recorded actual usage |

If a required capability cannot be tested, report PARTIAL with the precise missing
operation. A technically valid encode cannot pass an unreviewed motion or history
check. Record failure, reproduction, chosen correction and retest evidence; two
distinct failures of the same kind trigger the existing reroute rule.

## Preview boundaries and recovery

Registered/generated preview frames are checked against current producer contracts,
reference hashes and upstream lineage. Reviewed candidates also need a matching
review input hash. `preview_path` is an explicitly supplied independent preview
override: its origin is recorded, but it does not certify generated-asset lineage.
Do not use it to disguise a stale generated frame.

An interrupted cached picture must match its assembly receipt, manifest and input
clip hashes. On mismatch, preserve the work directory for inspection and regenerate
into a new clean work location; never accept it solely because duration/decode passes.

After this pilot, decide from recorded failures whether another Skill change is
needed. Successful one-project testing supports that tested workflow only; it does
not establish every Flow mode, model or artistic style.
